# Правила написания кода

> Техническое видение и архитектура: @doc/vision.md

## Стиль кода

- **Функции только** - БЕЗ классов и ООП
- **snake_case** для функций и переменных
- **Максимум 20 строк на функцию** - разбивать сложные функции
- **Явные типы** - указывать типы аргументов и возвращаемых значений
- **Docstring только для публичных функций** - краткое описание

## Асинхронность

- **async/await для всех I/O операций** (Telegram API, LLM API)
- **НЕ блокировать event loop** - использовать асинхронные библиотеки
- **Одна async функция = одна задача** - не усложнять

## Обработка ошибок

- **Fail Fast** - проверять входные данные сразу
- **Логировать ошибки** - `logger.error()` с контекстом
- **НЕ глушить исключения** - пропускать критические ошибки выше
- **Graceful degradation** - бот должен отвечать пользователю даже при ошибках LLM

## Работа с данными

- **Простые dict/list** - БЕЗ сложных структур данных
- **SQLite для персистентности** - все истории и прогресс в БД
- **Валидация входных данных** - проверять user_id, message content, длину сообщений
- **Ограничения** - max_message_length, max_pairs_*, max_image_size из конфига
- **БЕЗ мутации глобальных переменных** - передавать через параметры
- **JSON для хранения массивов** - content истории в виде JSON в БД

## Зависимости

- **Минимум импортов** - только необходимые библиотеки
- **БЕЗ * импортов** - явно указывать что импортируем
- **Группировка импортов**: stdlib, сторонние, локальные модули

## Логирование в коде

- **logger.info()** для важных событий (старт, новая история, запросы к AI)
- **logger.error()** для ошибок с stack trace
- **БЕЗ секретов в логах** - не выводить токены и ключи API
- **Контекст в сообщениях** - указывать user_id, story_id, длину сообщения, использование токенов
- **Примеры:**
  - `logger.info(f"User {user_id} started story {story_id}: genre={genre}")`
  - `logger.info(f"LLM request: model={model}, tokens={tokens}")`
  - `logger.error(f"Failed to generate cover for story {story_id}", exc_info=True)`

## Тестирование

- **Один тест = один сценарий** - простые функциональные тесты
- **БЕЗ сложных mock'ов** - тестировать реальное поведение
- **Основные флоу**: 
  - `/start` - приветствие нового пользователя
  - `/new_story` - создание истории с выбором параметров
  - `/my_stories` - просмотр списка историй
  - Процесс сочинения - чередование сообщений
  - Ошибки AI-сервисов (LLM, Speech, Image Gen)
- **pytest fixtures** для общих данных (конфиг, тестовые истории, mock AI responses)
- Используй uv для запуска тестов

## Безопасность

- **Фильтрация сексуального контента** - использовать moderation API или параметры LLM
- **НЕ логировать детские сообщения полностью** - только metadata (длина, timestamp)
- **Санитизация входных данных** - проверка длины сообщений (max_message_length)
- **Валидация изображений** - проверка размера и формата загружаемых файлов
- **Rate limiting** не требуется для MVP, но учитывать возможность
- **Изоляция пользователей** - истории каждого пользователя независимы

## Работа с AI-сервисами

- **Единая обработка ошибок** - все AI-запросы через try/except с логированием
- **OpenAI-compatible API** - все сервисы через единый интерфейс
- **Асинхронные вызовы** - все запросы к AI через async/await
- **Логирование использования токенов** - для контроля расходов
- **Graceful fallback** - при ошибке Image Gen продолжить без обложки
- **Температура из конфига** - использовать creativity_level из параметров истории

## Кроссплатформенность

- **Makefile с автоопределением ОС** - единый интерфейс для Windows и Linux/macOS
- **Python для управления процессами** - кроссплатформенный скрипт `scripts/daemon.py`
- **Docker для продакшена** - одинаковая работа на всех платформах
- **Тестировать на обеих платформах** - проверять работу на Windows и Linux

> Детали реализации: @doc/vision.md раздел "Деплой"

---

**Главное:** Читаемый, простой код без магии. Каждая функция делает одну вещь.
